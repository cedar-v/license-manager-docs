# 雪松授权云官方站群 GEO 优化计划

## 背景

雪松授权云当前已经形成由官网、官方文档、授权云产品和 GitHub 资源组成的官方站群：

| 站点 | 当前定位 | 目标职责 |
|------|----------|----------|
| `https://cedar-v.com/` | 公司与产品官网 | 产品认知、方案选择、价格说明和商业转化 |
| `https://docs.lm.cedar-v.com/` | 官方文档站 | 官方知识、技术证明、接入指导和问题排查 |
| `https://lic.cedar-v.com/` | 授权云产品 | 注册、使用、购买和实际业务操作 |
| `https://github.com/cedar-v/` | 开源与 SDK 资源 | 代码、版本、示例和外部技术证据 |

官网已经具备静态 HTML、独立主题页、canonical、robots、sitemap 和结构化数据等基础能力。文档站已经具备 AI 原生 API 快速接入、在线和离线激活、本地许可证校验、硬件指纹、SDK、API、排障、上线检查和客户案例等专业内容。

当前主要问题不在于缺少基础页面，而在于官方事实、站点索引、页面元数据、跨站关联、案例证据和效果监测尚未形成统一体系。部分旧页面、旧链接和搜索引擎缓存仍可能向用户或 AI 系统提供过期信息。

本计划用于指导下一阶段 GEO（Generative Engine Optimization，生成式引擎优化）建设。GEO 不作为独立于 SEO 的关键词工程，而是通过可抓取、可信、可引用、可归因和可持续更新的官方内容，提高雪松授权云在搜索引擎和生成式 AI 回答中的发现与引用概率。

## 目标

1. 建立唯一、可验证的产品和客户端接入事实源。
2. 消除官网、文档站、授权云和 GitHub 之间的失效链接与信息冲突。
3. 让全部有效页面可以被搜索引擎和 AI 搜索系统正确发现、理解和更新。
4. 让公司、品牌、产品、文档和代码资源形成清晰一致的实体关系。
5. 将现有技术实现、交付经验和案例转化为可被引用的第一手知识。
6. 建立可持续的 GEO 监测、复核和内容迭代机制。

## 目标用户

| 用户角色 | 主要问题 |
|----------|----------|
| 软件团队负责人 | 应该自研授权、使用 SaaS、选择私有化还是使用传统硬件方案 |
| 产品和商业负责人 | 如何设计试用、订阅、永久授权、续费和功能套餐 |
| 客户端开发工程师 | 如何完成激活、本地验签、设备绑定、心跳和离线授权 |
| 测试与交付工程师 | 如何验证到期、吊销、换机、断网、配置更新和异常恢复 |
| 企业采购与技术负责人 | 产品是否可靠，是否适合内网、离线和私有化场景 |
| 搜索与 AI 系统 | 哪些页面是最新、权威、可引用的官方来源 |

## 核心原则

1. **事实优先**：涉及接口、SDK、安全模型和产品能力时，必须以当前实现和可复现验证为依据。
2. **单一来源**：同一技术规则只保留一个权威解释页面，其他页面通过链接引用。
3. **官网与文档分工**：官网负责简明回答和商业选择，文档负责完整原理、证据和实施说明。
4. **先纠错再扩量**：先处理过期内容、失效链接和索引问题，再新增主题内容。
5. **证据优于口号**：性能、安全、兼容性、客户效果和合规结论需要提供验证方法或事实依据。
6. **中文主路径优先**：先稳定中文事实和内容结构，再同步英文版本。
7. **保持现有产品契约**：GEO 内容建设不修改服务端接口行为、SDK 契约或现有响应结构。

## 范围

### In Scope

1. 官网和文档站的抓取、索引、URL、sitemap、canonical 和结构化数据优化。
2. 公司、品牌、产品、文档和 GitHub 资源的实体统一。
3. 客户端接入契约、SDK、API、案例和旧页面的一致性治理。
4. 官网与文档站的双向信息架构和正文链接建设。
5. 高价值决策内容和产品证据内容建设。
6. Google、Bing、ChatGPT Search 等渠道的抓取与引用监测。

### Out Scope

1. 本计划不修改 License Manager 服务端接口和数据库结构。
2. 本计划不修改 SDK 的业务行为；发现差异时先形成问题清单，进入对应代码仓库处理。
3. 本计划不批量生成低价值关键词页面。
4. 本计划不承诺具体搜索排名、AI 推荐次数或固定流量结果。
5. 本计划不把 `llms.txt`、FAQ Schema 或其他单一技术标记视为 GEO 的主要手段。
6. 本计划不在事实未确认前发布性能、合规、安全或客户效果结论。

## 当前基线

1. 官网核心页面可以直接返回完整静态 HTML，具备基础抓取条件。
2. 官网不存在的路径当前可能返回首页和 HTTP 200，需要修复 soft 404。
3. `www.cedar-v.com` 当前 HTTPS 不可用，但历史搜索结果仍可能展示 www 地址。
4. 文档仓库当前约有 48 个 Markdown 页面，静态 sitemap 仅列出约 16 个 URL，开发者中心的多个核心页面未进入 sitemap。
5. 文档站多数页面共用相同 description、`og:url` 和 SoftwareApplication 结构化数据，缺少页面级 canonical。
6. 文档站 `robots.txt` 声明了实际不存在的 `sitemap.html`。
7. 部分旧页面仍引用 `https://api.lm.cedar-v.com`、`http://lm.cedar-v.com` 或 `https://www.cedar-v.com`。
8. 当前核心开发者文档要求首次在线激活前内置产品公钥，与已确认的实际接入规则不一致；首次在线激活应直接使用接口返回的产品公钥，心跳返回新许可证后继续使用同一产品公钥验签。
9. 已有案例具备场景价值，但部分代码、数据、评价和效果结论缺少当前实现或可核验证据。
10. 尚未建立统一的 AI 引用问题集、引用监测指标和定期复核流程。

## 工作项与验收标准

### GEO-01 建立唯一的客户端接入事实源

**优先级：P0**

**目标**

纠正公钥获取与许可证验签规则在现有页面中的错误表达，并建立唯一的客户端接入权威说明。现有授权模式边界已经具备完整说明，本工作项只统一入口和术语，不重新设计授权模式。

**工作内容**

1. 按以下已确认规则统一客户端接入文档：
   - 公钥是产品级公钥。
   - 首次在线激活不要求客户端预先内置公钥。
   - 激活接口同时返回 `license_file` 和 `public_key`；客户端使用本次响应中的产品公钥验证许可证，并将二者配对保存。
   - 心跳返回新 `license_file` 后，继续使用首次激活取得并保存的同一产品公钥，执行与激活后完全一致的验签、状态、有效期和设备指纹校验；全部通过后才替换旧许可证。
2. 以“许可证结构与验证”作为客户端信任模型和验签规则的权威页面，避免再新增内容重复的契约页面。
3. 修正 AI 原生 API 快速接入、在线激活、SDK 总览、排障、上线检查和相关案例中的公钥准备、保存和验签说明。
4. 将重复的公钥规则缩减为简要结论，并链接到“许可证结构与验证”权威页面。
5. 保留现有业务接入方式指导、操作指南和 AI 模板中的授权模式边界；只检查入口、术语和交叉链接是否一致，不重新推导或设计在线、首次联网、心跳、混合和纯离线模式。
6. 为权威规则增加生效日期、适用版本和变更记录，并说明旧版“发布前内置产品公钥”规则已经废弃。

**验收标准**

- 所有首次在线激活文档都明确说明不需要预先内置公钥。
- 激活相关文档都明确说明 `license_file` 与响应中的产品级 `public_key` 必须先配对验签，再配对保存。
- 心跳相关文档都明确说明新许可证沿用激活时保存的产品公钥，并执行与激活后一致的完整校验。
- API、AI 接入、SDK、许可证结构、案例和排障文档不再出现“忽略激活响应中的 `public_key`”或“首次在线激活必须预埋公钥”的现行规则。
- “许可证结构与验证”是唯一完整解释公钥信任模型的页面，其他页面不重复维护整套规则。
- 在线、首次联网、心跳、混合和纯离线模式沿用现有定义，相关入口和术语一致。
- 旧版内置公钥规则有明确的废弃说明，搜索用户能够找到新的权威页面。

### GEO-02 修复官方站群失效地址与 HTTP 状态

**优先级：P0**

**目标**

确保搜索引擎、AI 系统和用户访问到的所有官方入口稳定、唯一且返回正确状态。

**工作内容**

1. 为 `www.cedar-v.com` 配置有效 HTTPS 证书，并永久重定向到 `https://cedar-v.com/`。
2. 将官网不存在路径从首页回退改为真实 404。
3. 将文档中的 `https://www.cedar-v.com` 统一为主域名。
4. 核对并替换 `https://api.lm.cedar-v.com` 等旧 API 地址。
5. 将 `http://lm.cedar-v.com` 升级为 HTTPS，或明确标记为受限演示入口。
6. 在构建或发布流程中加入站内和站外链接检查。

**验收标准**

- 主域名、www、文档、授权云和 GitHub 入口均可正常访问。
- www 只执行一次 301 后到达主域名。
- 随机不存在路径返回 HTTP 404，不返回首页 200。
- 公开文档不再引用无法建立 TLS 连接的地址。
- 链接检查可以识别 404、TLS 失败和错误重定向。

### GEO-03 自动生成完整 sitemap 并刷新索引

**优先级：P0**

**目标**

让全部有效官网和文档页面进入可维护的索引发现机制，并缩短旧内容退出、更新内容重新抓取的时间。

**工作内容**

1. 官网和文档站改用构建时自动生成 sitemap。
2. sitemap 覆盖所有允许索引的中文、英文、政策和开发者页面。
3. `lastmod` 使用页面真实修改日期，不使用固定日期或构建时间冒充内容更新时间。
4. 删除 `robots.txt` 中不存在的 `sitemap.html` 声明。
5. 在 Google Search Console 和 Bing Webmaster Tools 提交 sitemap。
6. 发布新增、更新或删除页面后，通过 IndexNow 提交通知。
7. 对关键旧缓存页面请求重新抓取。

**验收标准**

- sitemap URL 数量与所有应公开页面数量一致。
- AI 快速接入、硬件指纹、本地验签、排障和上线检查均包含在 sitemap 中。
- sitemap 中不存在 404、重定向链或不应公开的内部页面。
- `lastmod` 与内容的实际修改历史一致。
- 搜索站长工具可以成功读取 sitemap，且无格式错误。

### GEO-04 建立页面级元数据、canonical 和结构化数据

**优先级：P0**

**目标**

让每个页面都能被搜索和 AI 系统准确识别其主题、首选 URL、作者、更新时间和内容类型。

**工作内容**

1. 为每个公开页面增加独立 title、description、canonical 和 `og:url`。
2. 为中文和英文对应页面增加 hreflang。
3. 文档页按内容类型使用 `TechArticle`、`Article`、`HowTo` 或适当的结构化数据。
4. SoftwareApplication 仅用于产品实体页面，不再注入到全部文档页。
5. 移除全站统一的 `price: 0` 等无法准确描述每个页面的字段。
6. 增加 `datePublished`、`dateModified`、author 和 reviewedBy 等可维护字段。
7. 确保结构化数据与页面可见正文一致。

**验收标准**

- 任取 10 个文档页面，其 description、canonical 和 `og:url` 均与页面内容和 URL 对应。
- 页面源代码中不存在统一指向文档首页的错误 `og:url`。
- 每页只有一个首选 canonical。
- 结构化数据通过语法校验，且不包含页面中不存在的产品、价格或能力。

### GEO-05 统一公司、品牌、产品与文档实体

**优先级：P1**

**目标**

让搜索和 AI 系统明确理解宁夏雪域科技、Cedar-v、雪松授权云、License Manager 和官方文档之间的关系。

**工作内容**

1. 确认并统一以下实体的正式名称、别名、Logo 和 URL：
   - 宁夏雪域科技有限公司。
   - Cedar-v / 雪松授权云品牌。
   - 雪松授权云软件产品。
   - 雪松授权云官方文档。
2. 为 Organization、Brand、SoftwareApplication 和 WebSite 设置稳定 `@id`。
3. 官网、文档站和产品页复用同一组实体标识。
4. 将作者和发布者从泛化的 `License Manager Team` 统一为真实公司或技术团队。
5. 连接官网、文档、授权云和 GitHub 官方资源。

**验收标准**

- 所有站点对公司、品牌和产品名称的使用一致。
- 同一产品不会因为 Cedar-v、License Manager 和雪松授权云等名称被解析成互不关联的实体。
- 每篇正式文档能够明确归因到公司、产品和审核团队。
- Logo、组织名称和官方 URL 不存在冲突。

### GEO-06 重建官网与文档站的双向内容路径

**优先级：P1**

**目标**

形成“用户问题—官网简答—文档证据—产品行动”的完整路径，避免官网和文档站重复维护同一正文。

**工作内容**

1. 为每个官网主题页建立对应的文档深度页面和具体章节链接。
2. 在文档中的方案选择、业务价值和案例页面提供适度的官网价格、私有化或咨询入口。
3. API 和排障页面保持技术导向，不插入干扰操作的销售内容。
4. 建立以下主题路径：
   - License 管理 → 授权生命周期 → API/SDK → 授权云。
   - 授权验证 → 本地验签 → 硬件指纹 → 错误排查。
   - 私有化部署 → 环境要求 → 离线模式 → 咨询评估。
   - 价格与选型 → SaaS/私有化对比 → 套餐或联系入口。
5. 增加面包屑、相关文档和下一步操作。

**验收标准**

- 用户从任一官网主题页最多两次点击可以到达对应技术证据页。
- 用户从技术文档可以明确找到产品入口，但不会被强制跳离当前任务。
- 官网和文档站不存在大段重复且需要双重维护的正文。
- 核心页面不只依赖页脚链接建立主题关系。

### GEO-07 清理旧 SDK、旧案例和不可验证结论

**优先级：P1**

**目标**

避免历史 SDK、旧 API 地址、示意代码和无依据结论损害接入正确性与官方可信度。

**工作内容**

1. 复核旧 Python、Go、C++ 和客户端模拟器页面的当前状态。
2. 对仍维护的 SDK 标注支持状态、版本、仓库和适用产品版本。
3. 对停止维护或仅供参考的内容增加明显状态说明，必要时下线或重定向。
4. 更新独立开发者案例中的旧 API 地址和 SDK 示例。
5. 复核机器视觉案例的业务规则、截图、客户反馈和实现细节。
6. 删除或改写无法提供依据的比例、性能、合规、安全和效果结论。
7. 区分标准产品能力、可选模块、定制能力和案例特定实现。

**验收标准**

- 公开代码示例可以按说明运行，或明确标注为伪代码。
- 所有 API 地址、仓库地址和下载链接均可访问。
- 客户评价和量化结果具备来源；无法证明时不作为事实发布。
- 案例不会把定制能力误写成所有版本默认具备的标准能力。
- 废弃页面有重定向或清晰的替代阅读路径。

### GEO-08 完善六个高价值决策主题

**优先级：P1**

**目标**

围绕用户真实决策和实施问题建设可被搜索与 AI 引用的第一手知识，而不是批量生成泛关键词文章。

**主题范围**

1. 自研授权、SaaS、私有化和加密狗分别适合什么团队。
2. 首次联网、持续心跳、混合模式和纯离线授权如何选择。
3. 稳定硬件指纹如何设计，以及为什么不依赖网卡信息。
4. 客户端为什么需要本地验签，公钥信任模型如何设计。
5. 按创建时间生效与按首次激活生效有什么区别。
6. 换机、解绑、续期、吊销和历史许可证迁移如何设计。

**统一结构**

- 开头提供可以独立引用的直接答案。
- 说明适用与不适用边界。
- 提供决策表、流程图或时序图。
- 给出常见失败场景和处理建议。
- 说明雪松授权云当前如何支持该场景。
- 链接到对应 API、SDK、配置或操作文档。
- 标注作者、审核人、发布日期和更新时间。

**验收标准**

- 六个主题均有一个权威主页面，不通过多个相似页面争夺同一主题。
- 每页包含直接答案、决策依据、产品实现、限制和相关文档。
- 内容包含雪松授权云的第一手经验，不只是整理行业通用知识。
- 页面可以独立帮助用户完成一次选型或设计决策。

### GEO-09 建立产品证据中心

**优先级：P2**

**目标**

将产品宣传结论转换为可以验证、引用和持续更新的事实资料。

**工作内容**

1. 建立当前支持能力矩阵。
2. 建立 SaaS、企业私有化、开源资源和可选模块的边界说明。
3. 建立 API 版本、协议 revision 和兼容策略。
4. 建立 SDK 语言、版本、平台和维护状态矩阵。
5. 建立在线、离线、心跳、换机、续期和撤销测试矩阵。
6. 建立性能测试方法、环境和结果页面；没有测试时不发布性能数字。
7. 建立安全设计、威胁边界和已知限制说明。
8. 建立公开更新日志、废弃通知和迁移说明。

**验收标准**

- 官网和文档中的主要能力结论都能链接到证据或明确的功能说明。
- 性能数字同时说明测试环境、数据规模、方法和时间。
- 安全页面同时说明保护能力与无法解决的风险。
- SDK、API 和产品版本的兼容关系可查询。
- 用户可以判断某项能力属于 SaaS、私有化、开源还是定制范围。

### GEO-10 建立 GEO 监测与迭代机制

**优先级：P2**

**目标**

用索引、引用和业务结果衡量 GEO 工作，避免只以页面数量或主观观感判断效果。

**工作内容**

1. 建立不少于 30 个固定测试问题，覆盖：
   - 品牌认知。
   - 产品选型。
   - 技术原理。
   - API 和 SDK 接入。
   - 故障排查。
   - SaaS、价格和私有化。
   - 行业和交付场景。
2. 定期记录 Google、Bing、ChatGPT Search 等渠道是否引用雪松授权云。
3. 记录被引用页面、答案准确性、旧内容残留和竞品来源。
4. 使用 Google Search Console 和 Bing Webmaster Tools 跟踪索引与查询表现。
5. 使用服务器日志确认 Googlebot、Bingbot、OAI-SearchBot 等抓取情况。
6. 统计来自 AI 和搜索渠道的访问、注册、咨询和购买转化。
7. 建立月度复核清单和问题修复闭环。

**验收标准**

- 固定问题集有版本记录，测试结果可以按月比较。
- 可以识别哪些页面被 AI 引用、哪些页面仍未索引或仍显示旧内容。
- 可以区分抓取问题、内容问题、权威性问题和转化问题。
- 每月形成一次问题清单、负责人、状态和下月优先级。

## 整体验收指标

### 正确性

- 关键技术规则与当前实现一致。
- 同一规则在不同页面中不存在互相冲突的结论。
- 公开链接、代码示例和下载资源有效。

### 可发现性

- 所有应公开页面进入 sitemap。
- robots、canonical、重定向和 HTTP 状态正确。
- 关键页面可以在站长工具中确认已发现或已索引。

### 可理解性

- 每页具有独立主题、description、canonical 和合适的结构化数据。
- 公司、品牌、产品和文档实体关系一致。
- 官网和文档站形成清晰的上下文链接。

### 可引用性

- 高价值页面包含直接答案、决策依据、限制、示例和证据。
- 性能、安全、客户效果和兼容性结论可以核验。
- 案例明确区分事实、客户反馈、示意代码和定制实现。

### 可持续性

- 页面更新可以自动刷新 sitemap 和 lastmod。
- API、SDK 和协议变更有版本与废弃机制。
- GEO 测试问题和引用结果可以持续记录与复盘。

## 风险与控制措施

| 风险 | 影响 | 控制措施 |
|------|------|----------|
| 未核对代码就统一文档 | 发布错误接入规则 | GEO-01 必须先完成实现核对和验证 |
| 同时大批改写官网和文档 | 增加重复内容和维护成本 | 先完成 GEO-06 内容映射，再确定正文归属 |
| 旧页面继续被搜索缓存引用 | AI 回答持续使用过期规则 | 使用重定向、sitemap、IndexNow 和重新抓取共同处理 |
| 案例数据无法证明 | 损害品牌可信度 | 删除无依据数字，事实、评价和推断分开表达 |
| 只追求页面数量 | 形成低价值内容 | GEO-08 限定六个高价值主题并设置统一验收结构 |
| 英文页面长期落后 | 产生双语事实冲突 | 中文稳定后按版本同步，未同步页面标注更新时间 |
| 结构化数据与正文不一致 | 搜索系统忽略或误解标记 | 自动校验并以可见正文为准 |

## 已确认决策

1. 官网与官方文档作为一个 GEO 内容体系统一规划。
2. 官网负责商业选择，文档站负责知识、证据和实施说明。
3. 优先推进事实一致性、失效地址和完整索引，不先批量增加文章。
4. 技术规则必须以当前实现为准，历史记忆和旧搜索缓存不能直接作为当前事实。
5. 中文主路径先完成，英文页面在中文稳定后同步。
6. `llms.txt` 可以保留，但不作为本计划的主要优化方向。
7. 本计划先落地为需求和实施依据，具体设计、修改和交付分别进入 `.ai/02-设计` 和 `.ai/03-交付`。
8. 产品公钥为产品级公钥；首次在线激活不要求预先内置公钥，激活接口返回许可证和产品公钥。
9. 心跳返回新许可证后继续使用激活时取得并保存的产品公钥，验签和完整校验规则与激活获取许可证时一致。
10. GEO-01 不盘点各 SDK 默认硬件指纹字段；各 SDK 的具体字段属于 SDK 使用说明和兼容治理范围。
11. 现有文档已经说明在线、首次联网、心跳、混合和纯离线模式边界，GEO-01 只统一入口、术语和交叉链接。
